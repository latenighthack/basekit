# Platform providers and dependency injection

Platform providers make OS and browser capabilities available to shared application
logic through small, typed contracts. The native host implements those contracts
and supplies them when constructing the client. Repositories consume capabilities;
use cases decide workflows; viewmodels expose progress and user actions. Native SDKs
retain responsibility for presentation, platform credentials and OS callbacks.

This guide supplements the [architecture](../multiplatform-architecture.md),
[ID rules](ids.md), [repository guidance](storage-and-repositories.md) and
[testing guide](testing.md). The contracts and factories below are illustrative
application code, not APIs automatically generated by Basekit or a compiled starter.

## Place contracts at the consuming boundary

Define a capability beside the shared layer that needs it. Export a curated set
through `:client` so a host can implement them without depending on implementation
modules. Keep the strict dependency chain `:client → :viewmodel → :usecase →
:repository → :api`; exports and module-owned construction factories carry the
required contracts through that chain.

| Dependency | Contract and consumer | Platform implementation |
| --- | --- | --- |
| Authentication, passkeys, session secrets | Repository boundary; identity/session repository | Native app or browser integration module |
| Push registration and permission | Repository boundary; notification repository | Native push adapter or browser service-worker adapter |
| External authentication and opening links | Repository capability when part of a workflow | Native/browser host, with an explicit presentation attachment |
| Connectivity and application execution signals | Shared infrastructure contract; synchronization coordinator | OS/browser observation adapter |
| Navigation, presentation acknowledgement, scene attachment | Client/viewmodel boundary | Basekit platform navigator and application shell |
| HTTP/WebSocket engine | API transport boundary | Target-specific transport implementation |
| Database delegate | Storage construction boundary | Target-specific ktstore database backend |
| Image fetching, decoding and rendering | Design-library presentation boundary | Native image pipeline or browser image element |

An SDK object, `Activity`, `UIViewController`, window, DOM element, native credential
or arbitrary JSON document must not become a repository parameter or viewmodel
field. Convert SDK values inside the adapter. Shared requests/results use canonical
types, including wrappers for **every** identifier: `LoginAttemptId`,
`CredentialId`, `RelyingPartyId`, `OAuthClientId`, `NotificationRegistrationId`,
`AccountId` and provider subject IDs. No raw strings or byte arrays stand in for IDs.
Use separate semantic types for secrets, proofs, challenges and URLs; keep primitive
encoding inside their boundary adapters.

Do not create one universal platform service with an `execute(String, Any)` method.
Define feature-specific capabilities with discoverable behavior and typed outcomes.
Only include capabilities the product uses.

## Specify outcomes, cancellation and availability

An authentication contract should distinguish a provider proof from an application
session. For example:

```kotlin
interface AppleLoginProvider {
    suspend fun authenticate(request: AppleLoginRequest): AppleLoginResult
}

data class AppleLoginRequest(
    val attemptId: LoginAttemptId,
    val nonce: LoginNonce,
)

sealed interface AppleLoginResult {
    data class Completed(val proof: AppleLoginProof) : AppleLoginResult
    data object Cancelled : AppleLoginResult
    data class Unavailable(val reason: CapabilityUnavailable) : AppleLoginResult
    data class Failed(val reason: AuthenticationFailure) : AppleLoginResult
}

interface PasskeyProvider {
    suspend fun authenticate(
        request: PasskeyAuthenticationRequest,
    ): PasskeyAuthenticationResult

    suspend fun register(
        request: PasskeyRegistrationRequest,
    ): PasskeyRegistrationResult
}
```

Use provider-specific proof/request types for Google, Apple and passkeys. For
passkeys, model the challenge, relying party, allowed credential IDs and assertion
fields explicitly. Preserve any standardized signed payload required for server
verification inside its dedicated proof type; avoid parsing and reserializing it
through untyped application maps.

`Cancelled` means the user dismissed the platform interaction; the sign-in screen
normally returns to idle. Coroutine `CancellationException` propagates as coroutine
cancellation. It must not become a user cancellation, generic failure or successful
result. Distinguish missing host, unsupported platform, unavailable credential,
configuration failure and provider/network failure with typed reasons.

A capability probe is advisory. Support does not imply enrollment, permission,
network access or a valid current presentation host. An unsupported implementation
returns `Unavailable`; it never supplies fake success. Avoid nullable dependencies
and silent no-op implementations where the workflow requires an outcome.

## Inject through the client composition root

See [composition, startup and lifecycle](composition-startup-and-lifecycle.md) for
module-owned factories, activation sequencing and account/runtime transitions.

The platform host constructs the adapters and calls the public client factory once
per application runtime. An application-specific aggregate might be:

```kotlin
data class ClientProviders(
    val appleLogin: AppleLoginProvider,
    val googleLogin: GoogleLoginProvider,
    val passkeys: PasskeyProvider,
    val sessionPersistence: SessionPersistenceProvider,
    val externalAuthentication: ExternalAuthenticationProvider,
    val externalLinks: ExternalLinkProvider,
    val notifications: NotificationProvider,
    val runtimeSignals: RuntimeSignalsProvider,
)

// Native/browser integration code constructs these implementations.
val client = Client.create(
    configuration = configuration,
    providers = platformProviders,
    execution = executionDependencies,
)
```

`SessionPersistenceProvider` represents a selected session mode, described below;
it does not require JavaScript to read an HttpOnly cookie. The aggregate is curated
for the product and platform exports. Split it into smaller groups if the language
bridge or feature boundaries benefit; do not force every app to implement unused
login methods or push.

Inside `Client.create`, pass dependencies down through each module's owned factory.
Each layer forwards construction dependencies and exposes only the contracts the
next layer needs. Do not import concrete repository implementations into `:client`
to assemble an unrestricted flat graph.

```text
Platform composition root
  builds adapters + transport/storage configuration + execution dependencies
  → Client.create
    → viewmodel-layer factory
      → usecase-layer factory
        → repository-layer factory
          → API/storage factories

IdentityRepository receives AppleLoginProvider / GoogleLoginProvider /
PasskeyProvider / selected session-persistence capability.
SignInUseCase receives IdentityRepository.
SignInViewModel receives SignInUseCase and its scoped navigator.
```

Use constructor injection and kotlin-inject bindings for module-owned graphs. Bind
the supplied instance to its interface; creating a second adapter inside a binding
can duplicate delegates, observers or credential state. For example, within the
repository's construction boundary:

```kotlin
interface IdentityPlatformBindings {
    val providers: IdentityProviders

    @Provides
    fun appleLogin(): AppleLoginProvider = providers.appleLogin

    @Provides
    fun passkeys(): PasskeyProvider = providers.passkeys
}
```

Here `@Provides` is kotlin-inject's annotation. Scopes and the containing component
are application/module declarations. Basekit's `@ViewModelInject` contributes
viewmodel bindings; `@ViewModelModule` integrates app-supplied provider modules in
the relevant generated components. These annotations do not create platform SDK
adapters or replace the layered client composition root. Keep repository capability
bindings in the repository graph; use the viewmodel integration seam for viewmodel
dependencies exposed by that graph. Do not resolve dependencies through a mutable
global singleton or service locator.

## Recommended platform defaults

These are the recommended starting choices for the reference architecture. They
are application dependencies, not bundled Basekit providers. Select compatible
versions and explicit OS/browser minimums; check feature support at runtime.

| Capability | iOS default | Android default | Web default |
| --- | --- | --- | --- |
| Apple login | [AuthenticationServices authorization controller](https://developer.apple.com/documentation/authenticationservices/asauthorizationcontroller) | Apple browser authorization with a verified app return and server exchange | [Sign in with Apple JS](https://developer.apple.com/documentation/signinwithapplejs) or server redirect flow |
| Google login | Official [Google Sign-In SDK](https://developers.google.com/identity/sign-in/ios/start-integrating) | [Credential Manager](https://developer.android.com/identity/credential-manager) with the Google credential integration | [Google Identity Services](https://developers.google.com/identity/gsi/web/guides/overview), following its browser/FedCM requirements |
| Passkeys | [AuthenticationServices public-key credential provider](https://developer.apple.com/documentation/authenticationservices/asauthorizationplatformpublickeycredentialprovider) | [Credential Manager](https://developer.android.com/identity/credential-manager), with required relying-party associations | Browser [WebAuthn](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API) |
| Persisted session secrets | [Keychain](https://developer.apple.com/documentation/security/keychain-services), with explicit accessibility policy | [Android Keystore](https://developer.android.com/privacy-and-security/keystore) encryption keys protecting an app-private encrypted payload | Server-set [Secure, HttpOnly cookies](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie) |
| External authentication session | [ASWebAuthenticationSession](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession) | [Auth Tab](https://developer.chrome.com/docs/android/custom-tabs/guide-auth-tab) where supported, with Custom Tabs fallback | Top-level redirect; popup only when its activation, callback and recovery contract is implemented |
| General external links | OS URL opening after scheme/target validation | OS intent resolution after scheme/target validation | Browser navigation with validated targets and safe new-window behavior |
| Push and notification presentation | APNs and [UserNotifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications) | [Firebase Cloud Messaging](https://firebase.google.com/docs/cloud-messaging/android/client) and native notification APIs | [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API), service worker and notification APIs |
| Connectivity hints | [NWPathMonitor](https://developer.apple.com/documentation/network/nwpathmonitor) | ConnectivityManager network callbacks | Online/offline events plus actual transport outcomes |
| Execution and foreground signals | Scene lifecycle; app lifecycle for app-wide policy | LifecycleOwner/ProcessLifecycleOwner plus Activity attachment | Page visibility/lifecycle plus explicit shell attachment |
| Image presentation | [Nuke/NukeUI](https://kean-docs.github.io/nuke/documentation/nukeui/) | [Coil ImageLoader and AsyncImage](https://coil-kt.github.io/coil/compose/) | Native browser image loading with the design library's loading/error treatment |

Use the OS's supported pickers, share sheets and clipboard APIs when adding those
features. Add narrow typed contracts only where shared logic needs their results;
a purely presentational operation can stay in the native design library. Do not
add a universal permission manager that hides differing OS semantics.

### Session persistence defaults

Keep short-lived access credentials in memory when practical. Persist only the
material required to restore the application session. Protobuf/ktstore records may
contain account, profile and linked-method metadata; authentication proofs and
refresh secrets do not belong in those ordinary stores or viewmodel state.

For iOS foreground-only restoration, start with
`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. If a defined background workflow
must restore secrets after first unlock, explicitly choose
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` and document the change in access
policy. Configure access groups, synchronization and migration deliberately. The
[WhenUnlockedThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessiblewhenunlockedthisdeviceonly)
and [AfterFirstUnlockThisDeviceOnly](https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlockthisdeviceonly)
documentation describes the protection choices.

Android Keystore protects cryptographic keys; it is not an arbitrary token database.
Use its keys with authenticated encryption to protect a small app-private session
payload. Specify atomic writes, backup exclusion, key invalidation and recovery.
Do not require biometric presence for every refresh unless the product deliberately
requires interactive restoration. `EncryptedSharedPreferences` is
[deprecated](https://developer.android.com/reference/androidx/security/crypto/EncryptedSharedPreferences);
do not prescribe it as the default for new integrations.

The browser default is a cookie-session transport mode. The server sets the cookie;
the browser attaches it under the configured credential policy. Shared session
logic observes authenticated server responses and can request restore/logout;
it never extracts the cookie into Kotlin. Model this as a distinct session strategy
or a capability with explicit supported operations, rather than pretending it is a
native read/write secret vault. Do not substitute localStorage or IndexedDB for
native secure session storage. Apply origin/CSRF policy, cookie scope and appropriate
SameSite rules; browser socket authentication must work without arbitrary upgrade
headers. HttpOnly limits script access to cookies; it does not eliminate XSS risks.

### Authentication defaults

The shared workflow is:

1. The repository begins a server authentication attempt, receiving a typed
   `LoginAttemptId` and provider-specific challenge/nonce configuration.
2. The platform provider presents the real SDK/browser interaction and returns a
   typed proof or another outcome.
3. The repository submits the proof to the generated API. The server verifies it
   against the attempt, expected issuer/audience, challenge and expiry.
4. The repository adopts the verified application session using the selected
   persistence strategy, then publishes session/account metadata through stores.

A native provider's success is not permission to enter the authenticated graph.
Keep method linking and passkey registration server-authorized and bound to the
current account. Configure Apple entitlements, associated domains, Android Digital
Asset Links, OAuth clients, redirect targets and web origins explicitly. Those
configuration identifiers also use ID wrappers once they cross an adapter boundary.

Use state/nonce and PKCE where the selected protocol requires them. Specify the
nonce representation for each SDK; raw and hashed nonce forms are not interchangeable.
Browser-to-app returns should carry a short-lived, one-use exchange code bound to
the initiating attempt and verifier, never access or refresh tokens in a URL.
Validate returns before redeeming through the API. Define response-loss recovery
without allowing proof replay to mint unrelated sessions.

### Notifications, runtime signals and images

Request notification permission in response to a meaningful user action, after
explaining the benefit. Client construction and startup do not open permission
dialogs. The provider handles OS permission/token events; the repository owns
server registration, token replacement, account association and durable action
processing. Treat a push token as a dedicated semantic value, not a raw string
used as an account or installation identifier.

Background callbacks enter a shared headless client entry point. They must not
require a destination, foreground presentation host or already-open socket. A
notification tap carries a typed routing intent; shared logic resolves access and
navigation. It does not automatically execute a delayed user decision.

Connectivity and lifecycle providers report observations. Shared coordinators
decide retry, refresh and reconnect policy. A reachable path or browser `online`
flag does not prove the server is available or the session is authorized. Inject
a wall clock for timestamps and monotonic time/scheduling for elapsed-time policy
so tests can control both; never infer elapsed duration solely from wall-clock time.

Image rendering remains a native design concern. Viewmodels expose typed image
references, revisions and loading eligibility; they do not expose platform bitmaps.
Use a reusable Nuke pipeline or Coil ImageLoader per configured security/cache
scope. Include revision and relevant account/security scope in cache identity;
configure authenticated requests and invalidate private caches on account change.
Do not put session tokens into image URLs. Museums use deterministic image fixtures.

## Separate adapter lifetime from presentation lifetime

| Scope | Owns | Release behavior |
| --- | --- | --- |
| Application runtime | Long-lived provider objects, SDK configuration, app-wide observers | Close owned registrations/tasks when the runtime shuts down |
| Account | Session persistence access, registered push association, private image cache policy | Stop account work, revoke/clear session as specified, retire account-bound callbacks |
| Scene/host | Current presentation anchor, Activity, browser shell attachment | Detach on host loss; never reuse a stale presenter |
| Attempt/destination | Credential interaction, callback delegate, awaiting coroutine | Complete once; cancel/detach when abandoned; reject late outcomes |

Resolve the current eligible host when an interaction begins. Do not permanently
capture the launch Activity or a SwiftUI view controller at client construction.
For multiple windows, use a typed `PresentationHostId` or equivalent scoped lease
to associate the action with the originating scene; an arbitrary active window is
not a reliable substitute. Keep native presenter resolution inside the adapter.

On iOS, present on the main actor and retain authorization delegates until terminal
completion. On Android, use lifecycle-aware Activity/result coordination; application
context does not replace an interactive Activity. On web, preserve user activation
for APIs that require it: prepare an eligible challenge ahead of the gesture or
synchronously reserve presentation access before asynchronous work when supported.
A network wait in a suspend function does not preserve activation automatically.

Coordinate concurrent taps and callback completion. Propagate cancellation, unregister
callbacks and fence late results with typed attempt/account generation identity.
Canceling a coroutine does not undo an external effect already accepted by a provider
or server; reconcile uncertain completion through the workflow's recovery contract.

State ownership explicitly in the client factory contract. Host-owned adapters are
closed by the host; client-owned adapters are closed by the client. Account logout
retires account state without tearing down reusable application providers. Avoid
duplicate listeners after Activity recreation, scene replacement or React remount.

## Qualify providers at three levels

Shared tests use deterministic provider fakes injected through the production
composition seam. Give fakes explicit controls for readiness, completion,
cancellation and callback delivery; replace sleeps with gates and assertions.
Exercise completed, cancelled, unsupported, missing-host, configuration-error,
provider-failure and coroutine-cancellation paths. Assert that no proof/secret reaches
viewmodel state, ordinary storage, navigation arguments or diagnostic output.

Full-server tests drive actual viewmodels, use cases, repositories, generated RPC
and session adoption with controlled provider proofs. Keep real server verification
enabled; use valid/invalid cryptographic fixtures and controlled issuer boundaries.
Test expired/wrong-attempt/wrong-audience/replayed proofs, response-loss recovery,
logout during an attempt, and two independent clients/accounts. Separate clients
get separate provider state and session persistence; they must not share a fake
global vault. Verify headless startup and cookie-session restoration separately
from native secret-vault restoration.

Platform integration tests use actual SDK/OS/browser paths to qualify presentation,
entitlements/associations/origins, user activation, callback URLs, secure storage
protection and permission behavior. Include host destruction/recreation, multiple
scenes, duplicate/late callbacks, offline return, key invalidation, push-token
rotation and private image cache isolation. A fake provider cannot establish these
platform guarantees. See [testing applications end to end](testing.md) for server
startup, multi-client and viewmodel test structure.
